At a glance

Overview

The SDK had no analytics layer. 1.6.0 adds one: a per-player session engine that watches playback and the player's own UI, emits typed events, and fans them out to sinks. A built-in Matomo sink turns them into Matomo requests.

1 · Architecture & files

Structure

Session state belongs to the widget, never the controller, because a feed shares one controller across all pages. Widgets below the player reach the session through an InheritedWidget scope. The controller only forwards commands to whichever session is attached.

New files: lib/src/analytics/{event, sink, config, metadata, session, scope}.dart · lib/src/analytics/matomo/{config, request_builder, sink, analytics_storage}.dart3

2 · Session lifecycle

State machine

A session reports only when it is active (on screen) and bound (its video is loaded). Each activation gets a new sessionId, which becomes Matomo's ma_id. A reload after an error keeps the session.

swipedAway

Feed page became preload: true again.

disposed

The player left the widget tree.

sourceChanged

Route or URL changed under the same player. A new session starts right away.

looped

A looping video wrapped while newSessionOnLoop is on (the default).

3 · Feeds: one view per swipe

Bytes-style PageView

Pages next to the current one are built with preload: true. They load and buffer but report nothing. When a swipe flips preload, _syncPreload ends the old page's session and activates the new one. Because the new page is already bound, its impression is immediate.

Config once

ChorkiPlayerController(analytics: config). Every page inherits it; a page's own analytics: wins.

Metadata per page

Give each page ChorkiMediaMetadata(contentId, title, feedIndex: i, ...) so Matomo can tell items apart.

No double counting

The controller's commands go only to the session passed in the latest attach(), which is always the visible page.

4 · Watched time & segments

ma_st · ma_se

video_player reports the position about every 500 ms. Between two ticks the session adds the position delta to the watched time, but only if the video was playing at both ticks, is not buffering, is not in an ad, and the jump is no bigger than 3 s × speed (larger jumps are seeks). The covered 5-second buckets are marked as watched (ma_se); watchedPercent is the share of the duration actually covered, so rewatching never counts twice.

_onValue() in chorki_analytics_session.dart · segmentLength (5 s) and heartbeatInterval (10 s) are set in ChorkiAnalyticsConfig6

Each error has transient and willRetry: only transient errors (network, timeouts, 5xx, video errors) are retried silently; a 401/403/404 or a missing video shows the error view at once. Silent retries after 1 s and 3 s emit retry auto: true, attempt: n. The Retry button emits auto: false. A page that failed off screen and becomes active emits auto: true. Errors while preloading are not reported.

video_player does not report automatic (ABR) rendition switches, so qualityChange covers only the viewer's picks in the Quality menu (fromHeight, toHeight, bitrate, label, auto). The current video height is also attached to every request as qualityHeight (mappable to a dimension).

8 · Ads: IMA → analytics

ChorkiAdLayer

The ad layer maps IMA events next to the existing onAdEvent forwarding, which is unchanged for host apps. Break boundaries come from the layer's own content pause/resume, so break duration and kind are measured even when IMA sends little. Every ad event carries the campaign id/title and the content's sessionId.

Content is frozen

During a break the session ignores the content's play state: no watched time, no pause/resume, no rebuffer. Swiped away mid-break? The session closes the break itself (interrupted: true).

Campaign context

The route's ad campaign id/title are set as session.adContext when the route resolves. They can be mapped to dimensions adCampaignId, adCampaignTitle.

Your callbacks still fire

ChorkiAdConfig.onAdEvent and onAdError behave as before. The analytics path is added next to them.

11 · Delivery: queue, batching, retry, offline

MatomoAnalyticsSink

Backoff after failures

Offline & restarts

Unsent requests are saved after every flush and when the app is hidden. On the next launch they are restored before new ones. Requests older than 23 h are dropped, because Matomo accepts a back-dated cdt beyond 24 h only with an auth token, which must never ship in an app.

Visitor identity

_id is 16 random hex characters, generated once and kept in storage. It is added at send time, so events queued before the storage loads still get the right id. uid is taken at event time, so a sign-in only affects later events.

Default storage is in memory. Plug in shared_preferences for persistence (example in section 12).

12 · Integration & Matomo setup

How to use it
// 1 · Once, at app start
final matomo = MatomoAnalyticsSink(
  const MatomoConfig(
    url: 'https://analytics.chorki.com',
    siteId: 3,
    dimensionIds: {
      'contentId': 1, 'seriesId': 2, 'category': 3,
      'contentType': 4, 'subscriptionTier': 5,
      'adCampaignId': 6, 'qualityHeight': 7,
    },
    storage: PrefsAnalyticsStorage(prefs), // optional
  ),
);
final analytics = ChorkiAnalyticsConfig(
  sinks: [matomo],
  consentGranted: userAcceptedAnalytics,
);

// 2 · On sign-in / plan change
matomo.userId = user.id;
matomo.setUserProperty('subscriptionTier', user.tier);

// 3 · Per player (or once on a feed's controller)
ChorkiPlayer(
  route: route,
  analytics: analytics,
  metadata: ChorkiMediaMetadata(
    contentId: 'ep-1042', title: 'Episode 4',
    seriesId: 'show-77', seasonNumber: 1, episodeNumber: 4,
    category: 'drama', contentType: 'episode',
  ),
);

Matomo server checklist

// shared_preferences-backed storage (in your app)
class PrefsAnalyticsStorage implements ChorkiAnalyticsStorage {
  PrefsAnalyticsStorage(this.prefs);
  final SharedPreferences prefs;
  Future<String?> read(k) async => prefs.getString(k);
  Future<void> write(k, v) async =>
      v == null ? prefs.remove(k) : prefs.setString(k, v);
}

15 · Testing, limits, next steps

Quality

Test coverage

  • Watched time freezes on pause, seek and ads
  • ma_se sends only new buckets
  • Loop → complete, loop, new ma_id
  • Scrub pause is not a pause
  • Preloaded page is silent; swipe → swipedAway
  • URL change: new impression waits for the new video
  • Break / drag cut off by a swipe never leaks into the next view
  • Exact Matomo params; offline → persist → resend
  • Exit before start; Chorki app naming, dims, shared visitor id
  • Consent off → nothing; a throwing sink is isolated
  • no_logging_test still passes (no print in lib/)

Known limits

  • ABR switches are invisible to video_player, so only manual quality picks are reported.
  • Dropped frames / bitrate are not exposed by video_player.
  • Fullscreen is not a player feature; set MatomoConfig.fullscreen if your layout always is.
  • Position ticks are ~500 ms apart, so watched time is accurate to about ±0.5 s per segment.
  • Media Analytics requires the premium plugin; without it only Events are useful.
  • Default storage is in memory: a new visitor per launch until you plug in persistence.
  • The ma_* request has no explicit pause/finish flag in the HTTP API; Matomo infers them from ma_st/ma_ps, plus our Events.

Before shipping

  • Run the example against a staging Matomo and check the Visits Log and Media reports.
  • Check that the Dart default user agent is not filtered as a bot by your Matomo; if it is, set MatomoConfig.userAgent.
  • Wire consentGranted to your consent UI.
  • Add a persistent ChorkiAnalyticsStorage.

Possible next steps

  • Bitrate and dropped frames once video_player exposes them.
  • A fullscreen flag when the player gets fullscreen.
  • Sampling for very high-traffic feeds.

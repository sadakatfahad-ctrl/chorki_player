Why: what goes wrong without guardrails

The problem

Code review catches what a reviewer happens to look at. Everything else drifts. With coding agents producing more change per day, the drift is faster, and the agent repeats whatever patterns it finds in the code, good or bad. Guardrails turn “we agreed” into “the build fails”.

1. Antipatterns spread

One catch (_) {} becomes forty-five. chorki_player had ~45 silent catches, five copies of the same _safe helper and an SDK that registered itself in the app’s DI container.

2. “Done” is not proven

Tests exist but do not check the thing that changed. A bug fix without a test that fails without it can silently come back. Coverage says code ran, not that it was checked.

3. Docs and code disagree

The README showed PlayerPage(claude{super.key}) (does not compile). The analytics table listed keys the code no longer sent. The CHANGELOG forgot renamed APIs.

4. Inconsistent structure

Mixed naming (a preloader class without the Chorki prefix next to ChorkiPlayer), an 848-line widget, magic durations, DateTime.now() scattered, making tests flaky and code hard to read.

5. Agents amplify all of it

An agent asked to “add an event” copies the nearest example. If that example uses a string literal key and no test, so will the next ten. Agents also stop when they think they are done.

6. Nobody can measure it

“Is the agent getting better? Did our new rule help?” Without fixed tasks and objective scoring, it is opinion.

Guardrails & Evals Playbook3

The model: nine layers of defence

Overview

Each layer catches a different class of problem at a different cost. Cheap, fast layers run on every keystroke; slow, thorough ones run nightly. A problem that slips through one layer is caught by the next.

Guardrails & Evals Playbook4

The full cycle of one change

Lifecycle

Follow one change, say “add an analytics event”, from request to release. The same script runs at every boundary, from fast to full. Nothing reaches main red, and every rule tightens over time through the feedback loop at the bottom.

Guardrails & Evals Playbook5

Ten principles

The ideas behind every layer

1. Every rule is a test

If a convention matters, a test fails when it is broken. A rule that lives only in a wiki is a wish. Put the enforcing test’s name next to the rule in the conventions doc.

2. Prove the guardrail first

Each rule is a pure function, run first on a tiny inline fixture with a known violation (and a known non-violation). A guardrail that cannot fail is decoration.

3. Ratchet, never big-bang

Record today’s violations per file in a baseline. New violations fail; fewer violations also fail until locked in. The count only goes down, so you can adopt a rule on day one without fixing 300 files first.

4. Escape hatches carry reasons

// guardrail:allow <rule> - <reason> on the line. No reason, no effect. Evals and reviewers count new allows, so the escape hatch is visible, not free.

5. One source of truth, everything else generated or compiled

Schemas generate README tables; README snippets are cut from compiled files; the public API snapshot is diffed against the CHANGELOG. Docs cannot drift if they are derived.

6. Determinism by injection

No wall clock, no unseeded randomness, no global singletons outside one file. Inject a clock and an id generator; tests and scenarios become exact.

7. Proof means “fails without the change”

A behaviour change needs a test that fails on the old code. A bug fix also needs a mutant that re-inserts the bug and must be killed. Coverage only shows code ran.

8. Fast inner loop, thorough outer loop

The quick gate takes seconds, so people and agents run it constantly. The full gate runs in CI, mutation testing nightly. One script, several depths, the same answers.

9. Agents get the same rules, enforced the same way

Agents read CLAUDE.md, but compliance comes from hooks: the agent cannot finish while the gate is red. Recipes (skills) encode the multi-file steps people forget.

10. Measure with evals, then improve the system

Fixed tasks, hidden tests, objective checks. Run them after changing a rule, a prompt or a model. If a score drops, the system regressed, not just the agent.

Guardrails & Evals Playbook6

Adoption roadmap

From zero to the full system

Each phase ends green and is useful on its own. A small team can do phases 0–4 in two weeks; phases 5–8 add proof and measurement. Never block the team: everything is ratcheted.

Minimum version
If you only have one day

1. A 60-line CLAUDE.md with a Definition of Done and the commands.
2. One gate script with --quick, wired to pre-commit and CI.

3. Three guardrails with baselines: swallowed errors, layering, file size.
4. A public API snapshot coupled to the CHANGELOG.

5. The agent stop hook running the quick gate.
Everything else in this playbook builds on these five.

Order matters. Conventions before rules (you need to know what to enforce); guardrails before gates (a gate needs something to run); scenarios before mutants (mutants need tests that can kill them); everything before evals (evals score against the gate).
Fix as you go. The audit list becomes the work queue. Each fix lands with the guardrail or test that would have caught it, so the fix stays fixed. In chorki_player each of ~25 audit findings has a test and most have a mutant.
Do not stop the world. Ratchets mean the team keeps shipping while the backlog shrinks. In chorki_player one refactor round took the undocumented exported API from 196 to 149 and the file-size backlog from 18 to 6; the next took both (and every other backlog) to 0. No freeze was needed.

Phase 0: audit the codebase

Know what to guard against

Read the code with one question per pass. Write every finding as where, what, why it matters, severity, and which guardrail would have caught it. That last column is the start of your rule catalog.

Six audit passes

  1. Errors: every catch, every fire-and-forget future. Is anything swallowed?
  2. Boundaries: imports between layers; globals; who owns DI; what leaks to the public API.
  3. Lifecycle: timers, streams, listeners; dispose paths; late callbacks after dispose.
  4. Determinism: clock, randomness, ordering, network in tests.
  5. Contracts: public API names, docs vs. code, CHANGELOG vs. API, payload schemas.
  6. Proof: which files and public methods no test touches; which tests assert nothing specific.
With an agent: run the passes as parallel read-only reviewers (one per concern), then merge, de-duplicate and verify each finding yourself before it goes on the list.

L0 Conventions as code

CLAUDE.md / CONTRIBUTING.md

One short file at the repo root that both people and agents read first. It is not a style guide: it is the working agreement. Every convention in it names the guardrail that enforces it, so the file cannot quietly become fiction.

Sections that earn their place

  1. What this is (2 lines) and who depends on it.
  2. Definition of done: numbered, checkable, with commands.
  3. Commands: a table, so nobody guesses flags.
  4. Architecture and layering: a tree plus the import rules.
  5. Conventions: each one sentence + the rule id.
  6. Ratchets: how baselines work, what never to do.
  7. Recipes: links to skills for multi-file changes.
  8. Gotchas: the things that bite new contributors.
Keep it under ~150 lines. Agents load it into every session; long files get skimmed by people and diluted for agents. Move detail into skills and CONTRIBUTING.md.

The Definition of Done (chorki_player, verbatim)

## Definition of done (every change)
1. `tool/check.sh` passes. Paste its tail in your summary or PR.
2. Behaviour change → a test or a scenario that fails without
   the change. Check this; don't assume it.
3. Bug fix → a regression scenario/test named after the bug and
   a mutant in `tool/mutants.yaml` that re-introduces it;
   `dart run tool/mutation_smoke.dart <id>` must say `killed`.
4. Public API change → intended diff in the API golden
   (`UPDATE_GOLDENS=1 flutter test test/guardrails`), and every
   changed symbol named in `CHANGELOG.md`.
5. Docs: `///` on new public members, README snippets edited in
   `example/lib/readme/` and copied verbatim, CHANGELOG sections.
6. Report honestly: what was verified, what was not, what failed.

L1 Analyzer and lints, ratcheted

The cheapest layer

Lints run in the IDE as you type, so they are the cheapest feedback there is. The catch: an analyzer rule cannot be allow-listed per file the way a test can, and the gate runs with --fatal-infos. The trick is to measure first and choose a path per rule.

L2 Guardrail tests: anatomy

Architecture rules as unit tests

A guardrail is an ordinary test that reads the source code instead of running it. Parse each file into an AST, walk it with a small visitor, collect violations, compare with the baseline. Use the language’s real parser, not regex: regex misses multi-line code and flags comments.

A complete rule (swallowed errors, simplified)

/// A catch must rethrow, convert, catch a narrow type,
/// or report to ChorkiDiagnostics.
List<Violation> swallowedErrors(SourceFile f) {
  final out = <Violation>[];
  f.unit.accept(_CatchVisitor((CatchClause c) {
    final body = c.body.toSource();
    final handled = body.contains('rethrow') ||
        body.contains('throw ') ||
        body.contains('ChorkiDiagnostics.report') ||
        c.exceptionType != null;   // on FormatException
    final line = f.lineOf(c.offset);
    if (!handled && !f.allows('swallowed_error', line)) {
      out.add(Violation(f.path, line, 'error swallowed'));
    }
  }));
  return out;
}

Its two tests: proof, then enforcement (abridged)

group('swallowed_error', () {
  test('catches empty catches and silent handlers', () {
    final f = fixture('''
void a() { try { x(); } catch (_) {} }          // 1: bad
void b() { try { x(); } on FormatException {} } // ok
void c() { try { x(); } catch (e, st) {
  ChorkiDiagnostics.report(e, st, 'c'); } }     // ok
void d() { try { x(); } catch (_) {} } // guardrail:allow
  swallowed_error - probe only                  // ok
''');
    expect(swallowedErrors(f).map((v) => v.line), [1]);
  });

  test('lib/ is within the baseline', () {
    expectRatchet('swallowed_error',
        onLib(swallowedErrors));
  });
});
The failure message is the documentation: it lists every file:line, says why, and gives the exact allow-comment syntax.

Adopt rules without stopping the world

fewerfaillock it in: UPDATE_GOLDENS=1 (rewrites downward only)

baselines.json (example; chorki_player’s is now {})

{
  "dartdoc": {
    "lib/src/analytics/chorki_media_metadata.dart": 5,
    "lib/src/theme/chorki_player_theme.dart": 32
  },
  "file_size": {
    "lib/src/analytics/chorki_analytics_session.dart": 5
  }
}

Per file, not a total. With a single total, fixing one file “pays” for a new violation in another. Per-file counts stop that trade.

Two switches, two different meanings

SwitchAllowed to
UPDATE_GOLDENS=1lower counts; rewrite the API golden if the CHANGELOG names every changed symbol
GUARDRAIL_RECORD=1record a brand-new rule’s first baseline. Never to hide new violations.

Allow comments

// guardrail:allow swallowed_error - a throwing
// onError handler must not break the player
} catch (_) {}

Matched on the line, the line above or the line below. An empty reason does not count. Evals score “no new allow comments”, so agents cannot use them as an exit.

Proving the guardrails; the API contract

Trust, but verify the checker

Fixture first, always

A rule that never fires looks exactly like a codebase with no problems. Every rule therefore has a fixture test with at least one violation and one deliberate non-violation. When the rule is changed, the fixture tells you if it still works, before it is run on the real code.

Real example: a gap a fixture exposed

Splitting the theme file into three files with a re-export made 6 public classes vanish from the API snapshot, because the snapshot builder did not follow export inside src/. The guardrail reported them as removed. Fix: follow re-exports, keeping every show/hide on the way, and add a fixture:

test('re-exports from src files are followed', () {
  // lib: export 'src/theme.dart' hide Hidden;
  // theme: export 'parts.dart' show Shown, Hidden;
  expect(names, unorderedEquals(['Theme', 'Shown']));
});
Also test the rule on the real tree in a known-bad state. The mutation smoke run (page 20) does this for behaviour; the eval self-tests (page 26) do it for the eval checks.

Guardrails & Evals Playbook14

Docs as code

Documentation that cannot drift

Docs drift because they are copies. Remove the copies: give each fact one owner and make every other place either generated from it or checked against it.

Compiled README snippets

Every code block in the README is cut from a file the build compiles:

// example/lib/readme/snippets.dart
// #region ads-markers
ChorkiPlayer(route: byteRoute, ...)
// #endregion

The README marks the block with <!-- excerpt: ads-markers -->; a test compares them after dedenting. Edit the source, copy verbatim.

Generated tables

The README’s event × keys table is rendered from the schema. The test regenerates it and compares; the failure message prints the new table to paste. No hand-maintained reference tables.

Same idea for config defaults, error codes, CLI flags: render from the code.

Changelog as a contract

  • top version = package version
  • only Added / Changed / Deprecated / Removed / Fixed / Security
  • every changed API symbol named
  • every @Deprecated listed
  • docs never recommend deprecated names

Executable specs anyone can read

Guardrails & Evals Playbook16

Writing scenarios; the coverage matrix

Specs as a living catalogue

Recipe: one scenario

  1. Name it after the behaviour, or the bug: 009_consent_granted_later.
  2. Write expect first, from the spec or the bug report, before running it.
  3. Run it. If it passes on the old code and it is a bug fix, it does not prove anything: sharpen it.
  4. If the actual output differs from your expectation, decide which one is wrong. Do not just paste the actual output in.
  5. Keep one concern per file; wide end-to-end flows use subsequence.
Antipattern: snapshot-and-forget. Copying the current output into expect turns a spec into a recording of whatever the code does today, bugs included.

A guardrail keeps the catalogue complete

Each event type must appear in at least one scenario’s expectations. Adding an event without a scenario fails the build, the same way a missing schema entry does.

L4 Conformance suites

Contracts for every extension point

Wherever users plug in their own code (a sink, a storage, a transport, a platform delegate), the library depends on a contract it cannot see. Write that contract once as a test suite, run every built-in implementation through it, and ship the suite so users can run their implementations through it too.

Framework-agnostic: a suite returns a list of (name, body) cases whose body throws on a broken contract. Hosts wire it to whatever test runner they use. No test-only dependency leaks into the shipped library.
// lib/chorki_player_testing.dart (shipped)
List<ChorkiConformanceCase> analyticsSinkConformance(
  ChorkiAnalyticsSink Function() create,
) => [
  ChorkiConformanceCase('sink: never throws for any event type',
      () async {
    final sink = create();
    for (final type in ChorkiAnalyticsEventType.values) {
      try { sink.onEvent(sampleAnalyticsEvent(type)); }
      catch (e) { throw ConformanceFailure('threw for $type: $e'); }
    }
    await sink.dispose();
  }),
  // tolerates unknown keys; flush/dispose idempotent;
  // events after dispose ignored; consent revoke works
];

// in the host app's tests
for (final c in analyticsSinkConformance(() => FirebaseSink())) {
  test(c.name, c.body);
}

Guardrails & Evals Playbook18

Errors cannot hide: diagnostics

No silent catches, and tests notice

A library should not log, and must not crash the host for a recoverable problem. So errors it recovers from go to one callback the host can route to Crashlytics or Sentry. The guardrail forbids catches that do neither, and the test config fails any test in which an unexpected error is reported.

What it found on day one: ad widget tests were silently getting HTTP 400 from the test HTTP client for VMAP fetches, and two “intentional throw” tests never asserted the error was reported. Both now declare what they expect.
// test/flutter_test_config.dart: runs around every test
Future<void> testExecutable(FutureOr<void> Function() testMain) async {
  final unexpected = <String>[];
  setUp(() {
    unexpected.clear();
    ChorkiDiagnostics.onError = (error, stack, context) =>
        unexpected.add('$context: $error');
  });
  tearDown(() {
    final reports = List.of(unexpected);
    ChorkiDiagnostics.onError = null;
    if (reports.isNotEmpty) {
      fail('Unexpected ChorkiDiagnostics reports: $reports');
    }
  });
  await testMain();
}

// test/support/diagnostics.dart: a test that expects reports
// swaps the failing collector for a recording one
List<String> captureDiagnostics() {

Anti-gaming checks every task inherits

  • made_changes: if the run changed nothing, the whole score is 0. Without this, an idle agent scores the baseline’s passing checks.
  • no_new_allow: adding guardrail:allow comments is visible and costs points.
  • baseline untouched: a baseline that grows is a fail unless the task says otherwise.
  • hidden tests: held-out, arrive after the agent.
  • judge with a rubric: “does each behaviour change have a test that fails without it” cannot be grepped.

Scoring and self-testing the harness

An eval must be able to fail

Scoring

# eval/rubric/common.yaml (inherited by every task)
- id: made_changes   weight: 1  # fail ⇒ whole score = 0
- id: gate_quick     weight: 3  # format, analyze, guardrails
- id: tests          weight: 3  # full suite
- id: hidden_tests   weight: 4  # held out
- id: no_new_allow   weight: 1
- id: no_wall_clock  weight: 1
- id: changelog      weight: 1
- id: proof          weight: 2  judge: fails-without-change test?
- id: scope          weight: 1  judge: stays within the task?
- id: conventions    weight: 1  judge: CLAUDE.md followed?

objective score = Σ weights of passing checks / Σ weights of all checks reported (task weights override common ones). The judge’s criteria are reported separately so a model’s opinion never hides a failing test.

Lesson learned: before the made_changes rule, an agent that did nothing scored 0.53 on the bug task: the untouched tree passes the gate, the tests, no-allow and no-clock. An eval must score an idle run at 0.

Self-test every task: idle → 0, reference → 1.0

Before trusting a task, run it twice with scripted “agents”: one that does nothing and one that applies the known answer. If idle scores above 0 or the reference below 1.0, the checks are wrong, not the agent.

What the self-tests caught

  • Idle runs scored 0.53 on the bug task: added made_changes, which zeroes the score.
  • Idle feature tasks scored 0.37–0.47: the harness copies the hidden tests into test/, and that counted as “made changes”. The check now ignores the harness’s own copy.

  • The docs task’s reference added an import and so failed “only comments in lib/”: the seed was rebuilt so only doc lines differ.

Ratchet helper (pseudo-code, any test framework)

function expectRatchet(rule, violations):
  actual   = countBy(violations, v => v.path)
  baseline = readJson("baselines.json")[rule] ?? {}
  grew   = [p for p in keys(actual, baseline) if actual[p] > baseline[p]]
  shrank = [p for p ... if actual[p] < baseline[p]]

  if env.UPDATE_GOLDENS and (empty(grew) or env.RECORD_NEW_RULE):
    writeJson("baselines.json", rule, actual); return
  if grew:
    fail("[rule] new violations: " + list(file:line + why)
         + " Fix, or // guardrail:allow rule - reason")
  if shrank:
    fail("[rule] fewer than baseline: lock in with UPDATE_GOLDENS=1")

function allows(file, rule, line):       # line, above, below
  for l in [line, line-1, line+1]:
    m = match(/guardrail:allow\s+(\w+)\s*[-:]\s*(.+)/, file.lines[l])
    if m and m.rule == rule and trim(m.reason) != "": return true
  return false

Ownership

  • Each rule has an owner and a one-line rationale in its doc comment.
  • Adding a rule: fixture first, record its baseline once, announce it.
  • Retiring a rule: when it never fires and a lint covers it, delete it.
  • Quarterly: review allow comments; delete those whose reason expired.

How guardrail systems fail (and the fix)

Slow gate → people bypass it

Keep the quick gate to seconds: parse once, share ASTs, push heavy work to CI and nightly.

Regex rules → false positives → allow-comment spam

Use the real parser. A rule with frequent false positives is worse than no rule.

Baselines that grow

Only a brand-new rule may record growth. Review baselines.json diffs like code.

Tests that assert the current output

Snapshot-and-forget scenarios lock bugs in. Write expectations first; mutants keep them honest.

Evals that agents can pass by doing nothing or by gaming

Self-test every task (idle 0, reference 1); hidden tests; diff-based checks; precision for review tasks.

Rules nobody understands

Every failure message says what, where, why and how to fix or allow it. If people ask in chat, improve the message.

Glossary

Guardrail test: a test that checks source code (structure, conventions, docs) instead of behaviour.

Ratchet / baseline: per-file count of accepted violations that may only go down.

Golden: a committed expected output (API snapshot, generated table) compared on every run.

Scenario: a declarative given/steps/expect spec run against the real engine.

Conformance suite: a shipped contract test for an extension point.

Mutant: a deliberate, known bug inserted to prove tests catch it (“killed”).

Quick / full gate: the same script at two depths: seconds for every edit, minutes for CI.

Eval task: a fixed request with objective checks, run in a throwaway worktree.

Seeded task: an eval whose starting state is a patch (a bug re-inserted, docs removed).

Self-test: idle and reference runs that prove an eval can tell good from nothing.
